# ヘルススコア再設計計画

## 概要

ヘルススコアを利用者ごとの調整値ではなく、インスタンスで共通する固定ポリシーとしてバックエンドで計算する。
既存のウィジェット側計算は置き換え、ウィジェットはバックエンドが配信したスコアと内訳の表示だけを担当する。

## 方針メモ

- 判断の軸は「機械資源の使用率ではなく、利用者が実際に使える状態を優先する」。
- API 失敗、Web ワーカー欠損、依存サービス停止は強く評価する。
- CPU、ホストメモリ、通信量は原因調査用の観測値として残すが、総合点の主要因にはしない。
- 欠測値、`NaN`、サンプル不足は危険値へ変換せず、評価対象外または `unknown` とする。
- 一つの通常閾値超過だけで0点にはしない。総合状態の `critical` は、API失敗率・Webワーカー欠損など直接的な利用不能か、複数劣化で60点未満になった場合に絞る。

## 設計方針

総合点は各指標の固定最大減点を加算して求める。指標の警告閾値から危険閾値までを線形補間し、各指標の減点上限を超えないようにする。

| 指標 | 警告開始 | 危険 | 最大減点 |
| --- | ---: | ---: | ---: |
| API内部エラー率 | 0.5% | 2% | 25 |
| Webワーカー稼働率 | 100%未満 | 79%以下 | 12 |
| ワーカー再起動（10分） | 2回 | 5回 | 5 |
| Webワーカー応答遅延 | 120ms | 250ms | 3 |
| API P95 | 800ms | 2,000ms | 20 |
| inbox最古待機 | 60秒 | 300秒 | 10 |
| deliver最古待機 | 15分 | 60分 | 5 |
| DB応答 | 200ms | 500msまたは疎通不能 | 10 |
| Redis応答 | 50ms | 150msまたは疎通不能 | 5 |
| ワーカーRSS | 800MB | 1,200MB | 3 |
| ディスク空き | 15%または10GiB | 5%または2GiB | 2 |

API内部エラー率は20件以上のサンプルかつ5件以上の内部エラーがある場合だけ評価する。DBまたはRedisが疎通不能なら40点、Webワーカーが全停止なら20点を総合点の上限とする。

- 可用性: API 内部エラー率、Web ワーカー生存率、再起動回数
- 応答性: API P95、Web ワーカーのイベントループ遅延とハートビート
- バックグラウンド処理: inbox / deliver の最古待機時間、queue ワーカー生存率
- 依存サービス: DB / Redis の疎通と遅延
- 枯渇リスク: ワーカー RSS、ディスク空き容量

## 機能一覧

| 機能 | 実装方法 | 方式 |
| --- | --- | --- |
| API 内部エラー率 | API 実行結果を5分窓へ記録 | 5xx相当だけを対象にし、サンプル数と絶対件数の下限を設ける |
| ワーカー生存監視 | 各ワーカーの定期報告をスロット単位で集約 | 15秒以上報告がないワーカーを欠損扱い |
| ワーカー再起動監視 | master の exit ハンドラから再起動イベントを配信 | 10分窓で回数を評価 |
| キュー待機時間 | Bull の最古 waiting ジョブ時刻を取得 | inbox と外部 deliver で閾値を分ける |
| ディスク残量 | 低頻度でファイルシステム容量を取得 | 割合と絶対空き容量の厳しい方を採用 |

## 非実装

| 項目 | 理由 |
| --- | --- |
| 利用者ごとの重み・閾値設定 | 同じインスタンスに複数の評価が生まれるため |
| 外部インスタンスの到達不能数による減点 | 相手側の障害で自インスタンスの総合点が下がるため |
| 自動学習による閾値変更 | 長期的な劣化を正常として学習する危険があるため |
| DB サーバー側のディスク監視 | アプリとは別VMであり、このプロセスから安全に取得できないため |

## 決定事項

| 項目 | 決定 |
| --- | --- |
| 計算場所 | バックエンド |
| ポリシー | ソースコード内の固定値 |
| ウィジェット設定 | ヘッダー表示と透過だけ |
| 本番反映 | ユーザーが行うため、この作業ではローカル実装と検証まで |

## 実装手順

1. 純粋なスコア計算モジュールと単体テストを追加する。
2. API、ワーカー、キュー、ディスクの観測値を追加する。
3. `healthStats` 配信へ計算結果を含める。
4. ウィジェットを表示専用へ変更し、表示文言を更新する。
5. テスト、型チェック、クライアントビルドを実行する。
6. 変更内容とユーザーがデプロイするときの注意点を引き継ぐ。
