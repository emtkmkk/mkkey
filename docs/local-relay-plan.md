# 双方向ローカルリレー

## 概要

もこきーと cp.mkkey.net が互いの通常のリレーとして購読し、第三のリレーを経由せずローカル投稿を届ける。判断の軸は、もこきー内の公開範囲とリモート向け制限を維持すること。

## 配置と構成

購読は既存の署名検証済み inbox と Follow(Public)／Accept／Undo を使い、[local-relay.ts](../packages/backend/src/services/local-relay.ts) が許可ホストと購読状態を確認する。[購読モデル](../packages/backend/src/models/entities/local-relay-subscriber.ts) を新設する。通常フォローとは用途を分け、古い解除要求で新しい購読が消えないよう Follow ID を保存する。

[作成ジョブ](../packages/backend/src/services/note/ap-deliver.ts)、[削除](../packages/backend/src/services/note/delete.ts)、[アンケート更新](../packages/backend/src/services/note/polls/update.ts) で購読者を通常配送先へ追加する。同じ inbox はまとめる。HTTP署名・失敗時再試行は既存の配送キューを使う。

## 方針メモ・設計方針

- 送るのは自サーバーで作られた public/home 投稿だけ。受信した他サーバーの投稿をリレーへ送り返さない。
- もこきーの public/home＋localOnly は cp をローカル範囲とみなし配送する。既存の `_mk_localVisibility` とバブル設定による復元を使う。
- セミパブリックは通常のリモートに公開として届け、cp には元の home を既存拡張で伝える。純粋なリノートも同様。
- cp 側で明示的に「連合しない」とした投稿は追加配送しない。

## 機能一覧・決定事項

- もこきー→cp と cp→もこきーの両方向。
- フォロワー関係がなくても、購読成立した相手に public/home を届ける。
- followers／specified は通常の宛先にのみ送る。
- 許可ホストを外すと、保存済みの購読があっても追加配送を止める。
- 削除・Undo(Announce)・アンケート更新も同じ相手へ送る。
- ユーザー削除・凍結も、通常フォローのない購読相手へ通知する。
- 「リモートフォロワーのみ」の投稿を引用・リノートした場合も、共有範囲の相手だけに配送する。第三のホストへは広げない。
- 配送順が前後しても返信先を解決できるよう、購読済みの相手からの署名付き取得を public/home に限って許可する。署名が必要な応答は共有キャッシュを禁止する。

## 非実装

過去投稿の一括取り込みは行わない。無関係な外部投稿を転送する汎用リレーにはしない。限定投稿の公開範囲を拡大しない。

## 実装手順

1. 両リポジトリに購読の保存と Follow／Undo を追加する。
2. 投稿・削除・更新の配送先に購読者を加え、既存の公開範囲復元を補完する。
3. 購読・解除・重複・制限・ループ防止・セミパブリックのテストを実施する。
4. 両側をマイグレーション・デプロイして許可ホストを設定する。
5. cp のリレーに `https://mkkey.net/inbox`、もこきーのリレーに `https://cp.mkkey.net/inbox` を登録し、両方の承認と実配送を確認する。cp のバブル対象に mkkey.net、もこきーのおすすめ対象に cp.mkkey.net が含まれていることも確認する。

## ローカル検証

`pnpm test:local-relay` で実ソースの購読・解除・範囲・取得ルートを検証する。隣に `mkkey-cp` のチェックアウトがある環境では、両側の実装を組み合わせた相互購読テストも実行する。単独チェックアウトではその1件だけスキップする。

導入は双方のコードとマイグレーションが揃ってから行う。既存の外部リレーの削除は、双方向の実配送確認が済んでから判断する。
